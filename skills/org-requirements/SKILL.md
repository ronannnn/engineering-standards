# 01 需求分析（org-requirements）

## 何时使用

- 新需求、需求变更、或别人给了一段模糊诉求要你落地时。
- 已有 `01-requirements.md` 但被门禁打回、需要补齐验收标准时。

不适用于纯机械改动（改文案、升依赖小版本）——这类改动在 01 写 `不适用` 并说明理由，直接进入 04。

## 输入

| 输入 | 要求 |
|---|---|
| 用户诉求 | 原始描述，含提出人、业务背景、期望效果 |
| 现有代码 | 存量项目必须先读：相关模块、接口、表结构、部署方式 |
| 上游约束 | 合规、预算、工期、依赖团队 |

## 产出

`docs/engineering/<slug>/01-requirements.md`，编号 `REQ-0001`。

## 步骤

1. **先做现状分析，再写需求。** 打开相关代码与配置，把「现有怎么做的、能复用什么、会冲突什么」写进 `## 现有系统分析`。绿地项目写 `不适用：绿地项目，无既有代码`。
2. **列出歧义再动笔。** 把「不确认就会做错」的问题写成 `## 风险与开放问题` 表格（问题 / 影响 / 需要谁决定 / 截止时间）。不要用假设填空。
3. **写功能需求。** 每条 `### FR-N` 必须有描述、优先级、以及 Given / When / Then 三行场景。Then 必须是可观测结果，不是「代码写好了」。
4. **写非功能需求。** 每条带数字：P95 延迟、QPS、数据量、可用性、兼容窗口。没有数字的 NFR 等于没写。
5. **写验收标准表。** 每行：编号、对应需求、判定方式、是否可自动化。判定方式要能让另一个人照着做一遍。
6. **明确非目标与范围外。** 越清楚越好，这是防止范围蔓延的唯一手段。
7. **自检后交人签收。** 把 `状态` 从 `草稿` 改为 `待签收`，请需求决策人确认；对方确认后由对方把 `状态` 改为 `已冻结`、填 `签收` 与 `签收时间`。

## 冻结

- 只有人能冻结 01。你不要代填签收人，也不要把 `状态` 直接写成 `已冻结`。
- 冻结后下游只读。要改：`状态` 回 `待签收`、`修订` +1，重新走签收。

## 门禁

```bash
python3 gates/run.py docs/engineering/<slug> --stage 01
```

必须全绿才能交签收。常见失败：缺 Given/When/Then、NFR 没有数字、验收标准表缺列、现有系统分析少于 20 字。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 先想方案再写需求 | 需求被方案绑架，验收标准照着实现写 | 只写用户能观测到的结果 |
| 验收标准写成任务清单 | 06 矩阵审计无法对应，评审无法判定 | 每条 AC 对应一个可执行判定 |
| NFR 写「性能良好」 | 无法验收，后期扯皮 | 写 P95、QPS、数据量等具体数字 |
| 「不适用」不写理由 | 门禁拒绝 | `不适用：<具体原因>` |
| 自己把状态改成已冻结 | 等于伪造签收 | 只改到 `待签收` |

## 交接

冻结后把 `01-requirements.md` 路径与其中未决问题一并交给架构师（`org-role-architect`），由它用 `org-design` 进入 02。
