# 08 维护与复盘（org-retro）

## 何时使用

- 一次需求交付完成、上线观察窗口结束之后。
- 线上问题处理完、需要回溯流程漏洞时。

## 输入

| 输入 | 要求 |
|---|---|
| 01–07 全部产物 | 复盘要对着冻结产物说话，不凭记忆 |
| 运行数据 | 指标、告警、工单、返工记录 |
| 人的反馈 | 哪个 gate 卡得值、哪个 gate 是形式 |

## 产出

`08-retro.md`，编号 `RTR-0001`。

## 步骤

1. **结果对照。** 从 01 抄目标，写实际结果与差距。差距要写数字，不写「基本达成」。
2. **过程偏差。** 哪些阶段返工、哪些门禁误报或漏报、哪些环节比预期慢。给事实与耗时，不给情绪。
3. **裁定清单。** 把过程中你自己拍板的地方全部列出：位置、决定、理由、若错了代价。这份清单是追责与改进的依据。
4. **标准改进项。** 每条必须指向本仓库里的具体文件（`skills/`、`templates/`、`gates/`、`policies/`、`AGENTS.md` 等），写清现状、建议改动、优先级。改进项空转等于复盘失败：连续两次写「无」，说明标准已脱离实际。
5. **后续行动。** 谁、做什么、什么时候、对应哪条改进项。
6. **确认。** 由人确认（不是每份都必须走，但涉及标准改动的要）。

## 冻结

- 08 可以 agent 冻结（`签收: 机器门禁`），也可以人确认。
- 改进项落地时，改本仓库文件、跑 `python3 -m unittest discover gates/tests`、在 `CHANGELOG.md` 记录。

## 门禁

```bash
python3 gates/run.py docs/engineering/<slug> --stage 08
```

常见失败：结果对照缺列、标准改进项目标文件不在本仓库、优先级不是 高/中/低、签收为空。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 复盘写感想 | 下次同样踩坑 | 每条偏差对应一个可改的文件 |
| 改进项写给「别人」 | 无法落地 | 写成本仓库的具体改动 |
| 只复盘成功项 | 问题被掩盖 | 偏差优先，失败优先 |
| 改进项写了不改 | 标准腐烂 | 当次或下一个需求内落地并跑自测 |
| 复盘跳过门禁 | 格式不齐，无法检索 | 跑 `--stage 08` 后再冻结 |

## 交接

改进项落地后，标准仓库发一次 `CHANGELOG.md` 更新；如果改动了门禁或模板，必须同时更新对应 `SKILL.md`（三处同源）。

## 本次契约补充

08 在上线观察或故障恢复后进行，不作为上线前的完成条件。记录影响、恢复证据与后续任务；任务有负责人、期限、状态及链接。持续维护的缺陷、漏洞和升级新建需求。标准改进参考 [三类实际试跑](../../policies/workflow-evaluation.md)，实际试跑与脚本自测分开；完整归档使用 `--all`。

## 模块与子模块

模块 08 指向根 07，分别记录模块问题及后续任务；根 08 汇总跨模块问题。归档要包含全部登记模块。组织、引用、命令与迁移见 [模块资料规则](../../policies/modular-artifacts.md)。
