# 04 开发计划（org-plan）

## 何时使用

- `02-design.md`（及有界面时的 `03-ui-design.md`）已冻结，准备开工前。
- 实施中发现任务拆分不合理，需要回退重拆时。

## 输入

| 输入 | 要求 |
|---|---|
| `01-requirements.md` | 所有 AC，用于验证矩阵 |
| `02-design.md` | 接口契约、数据模型、迁移与回滚 |
| `03-ui-design.md` | 页面清单与交付说明（有界面时） |

## 产出

`04-tasks.md`，编号 `TSK-0001`。

## 步骤

1. **按依赖排序拆任务。** 每个 `### 任务 N：<标题>` 必须写：文件（具体路径）、依赖（无 / 任务 N）、验收方法（可直接执行的命令 + 期望结果）、对应需求（FR-N）。
2. **控制粒度。** 一个任务应能在一次提交内完成、并通过自己的验收命令；超过 5 个文件的改动要拆开。不要把「写全部测试」和「写全部实现」各当成一个任务。
3. **先写验证矩阵。** 每行：场景、覆盖任务、验证类型（单元/集成/e2e/手工）、对应验收标准。01 里的每一条 AC 至少要有一行，缺行会在 06 的矩阵审计里暴露。
4. **写里程碑与暂停点。** 分几批、每批结束的可验证状态、什么情况下停下来等人。
5. **写风险与回退。** 最可能失败的任务、失败后的处理、是否可独立回滚。
6. **自动冻结。** 门禁通过后把 `状态` 置 `已冻结`、`签收: 机器门禁`、填 `签收时间`。

## 冻结

- 04 不给人签收（`不适用` 也不允许）：计划是执行的输入，由门禁判定完整性。
- 计划变更属于正常情况：改完后 `修订` +1，重新跑门禁，并在 05 里记录偏差。

## 门禁

```bash
python3 gates/run.py docs/engineering/<slug> --stage 04
```

常见失败：任务编号不连续、任务缺文件/依赖/验收方法、任务没有具体文件路径、验证矩阵为空或列缺失。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 任务写成「实现后端」 | 05 无法逐条交证据 | 拆到能一次提交、一条命令验证 |
| 先写实现任务后补测试任务 | TDD 顺序被打乱 | 每个任务自带测试步骤 |
| 验收方法写「跑测试」 | 05 记录无法证明 | 写完整命令与期望输出 |
| 验证矩阵漏 AC | 06 矩阵审计直接失败 | 每条 AC 至少一行 |
| 计划里塞重构 | 交付范围膨胀 | 重构单独成需求或标为范围外 |

## 交接

冻结后把 `04-tasks.md` 交给开发（`org-role-dev`），由它按任务顺序执行 `org-implement`。
