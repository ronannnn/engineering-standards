# 02 技术设计（org-design）

## 何时使用

- `01-requirements.md` 已冻结，需要把需求翻译成可实施、可回滚的技术方案时。
- 已有设计被评审打回（缺备选、缺迁移回滚、影响面漏勾）需要修订时。

## 输入

| 输入 | 要求 |
|---|---|
| `01-requirements.md` | 必须 `已冻结`；读完所有 FR、NFR、AC、开放问题 |
| 现有代码 | 将被改动的模块、接口定义、表结构、部署配置；以路径为证 |
| 上游方案 | 已有同类实现、框架能力、团队约定 |

## 产出

`02-design.md`，编号 `DES-0001`。

## 步骤

1. **先勾影响面，再写方案。** `## 变更影响面` 的五项（schema / 权限模型 / 跨模块接口 / 新增依赖 / 性能基线）先如实勾选：勾中任意一项，本阶段就必须人签收。先勾选能防止「写完才发现要迁移」。
2. **读代码，不凭记忆。** 把要改的文件打开看一遍，设计里引用真实路径与符号。禁止写「相关模块」。
3. **给至少两个真实备选。** 每个备选写：做法、优点、缺点、为何未选。凑数的备选（同一个方案换个名字）会被评审直接打回。
4. **写接口契约。** 表格：接口 / 方法 / 请求 / 响应 / 错误。没有跨模块接口时写 `不适用：<理由>`。
5. **写数据模型与迁移。** 有 schema 变更时必须写：结构、迁移步骤、旧数据处理、回滚方案。缺回滚视为设计未完成。
6. **写安全与权限。** 必须覆盖认证（谁进来）、授权（谁能做什么，越权如何拒绝）、敏感数据（采集/传输/存储/日志/导出）。
7. **写验证方式。** 设计如何被证明：契约测试、迁移演练、压测、灰度对比。没有验证方式的设计不可签收。
8. **交人签收（条件触发）。** 勾中影响面任一项：把状态改 `待签收`，由人冻结。未勾中：可直接标 `已冻结`，`签收: 机器门禁`。

## 冻结

- 影响面任意一项被勾选 → 必须人签收；用 `签收: 机器门禁` 会被门禁拒绝。
- 冻结后若要改接口或表结构，回到本阶段、`修订` +1、重新签收。

## 门禁

```bash
python3 gates/run.py docs/engineering/<slug> --stage 02
```

常见失败：备选方案少于两个、备选缺「为何未选」、勾了 schema 变更但数据模型写 `不适用`、安全与权限缺认证/授权/敏感数据之一、验证方式为空。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 只有一个方案 | 评审无法判断取舍，返工概率高 | 至少两个真实备选，写清放弃理由 |
| 影响面漏勾 | 本该人签收的设计被自动放行 | 写方案前先逐项诚实勾选 |
| 迁移只写正向 | 上线出问题无法回退 | 迁移与回滚成对出现 |
| 安全写「沿用现有」 | 新接口可能引入越权 | 写清本方案的认证/授权/敏感数据落点 |
| 把实现细节当设计 | 设计文档变成代码翻译 | 设计写边界与契约，实现细节留给 05 |

## 交接

冻结后把 `02-design.md` 与接口契约表交给 UX（`org-role-ux`，有界面时）与开发（`org-role-dev`），由它们分别进入 03 与 04。

## 本次契约补充

设计读取项目现有语言、框架、部署与验证方法，优先复用已有边界。方案变化按 [返工规则](../../policies/lifecycle.md) 更新修订，并让受影响的下游产物重新验证。

## 模块与子模块

根资料维护公共目标、架构或设计规范，模块与子模块在同路径的阶段文件写具体内容；声明依赖并固定公共修订，避免复制共享事实。组织、引用、命令与迁移见 [模块资料规则](../../policies/modular-artifacts.md)。
