# 05 编码实现（org-implement）

## 何时使用

- `04-tasks.md` 已冻结，开始逐任务写代码时。
- 修 bug 或补测时（同一套证据要求）。

## 输入

| 输入 | 要求 |
|---|---|
| `04-tasks.md` | 必须 `已冻结`；任务顺序即执行顺序 |
| `02-design.md` | 接口契约、数据模型、错误处理约定 |
| 真实代码库 | 先读同一模块现有写法，保持一致的抽象层级 |

## 产出

- 代码与测试本身。
- `05-implementation.md`（证据台账），编号 `IMP-0001`。

## 步骤

1. **单任务闭环。** 取第一个未完成任务：写一个会失败的测试（RED）→ 跑它并记录命令与失败摘要 → 写最小实现 → 再跑同一命令（GREEN）→ 记录通过摘要 → 提交。
2. **证据当场记录。** 每完成一个任务就把这一段写进 `## 任务执行记录`，不要事后补。事后补的证据无法自证顺序。
3. **偏差显式化。** 与 04 不一致的地方（多改的文件、多加的分支、跳过的任务）写进「与计划的偏差」，并说明原因；重大偏差要回到 04 改计划。
4. **保持变更面等于评审面。** 不动与任务无关的文件；顺手改的格式、重排、改名单独成提交或不做。
5. **每个任务结束跑一次局部验证。** 只跑该任务相关的测试，不跑全量（全量留给 06 与 CI）。
6. **自动冻结。** 所有任务完成后跑门禁，全绿后置 `已冻结`、`签收: 机器门禁`、填日期。

## 冻结

- 05 不给人签收，但「已冻结」的代价是：每条 RED/GREEN 都有命令和输出摘要。缺一条门禁不放行。
- 发现 04 拆错了任务：先改 04（修订 +1、重跑门禁），再继续，不要在 05 里偷偷多做一个任务。

## 门禁

```bash
python3 gates/run.py docs/engineering/<slug> --stage 05
```

常见失败：任务数与 04 不一致、某任务缺测试命令、RED 或 GREEN 缺命令/输出摘要、变更文件表为空。

## 常见错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 先写实现再补测试 | 测试照着实现写，证明不了行为 | 先让测试失败，看到失败再实现 |
| 只写「测试通过」 | 无法复核，等于没证据 | 贴命令与输出摘要（含通过计数） |
| 把编译通过当测试 | 逻辑错误被放行 | 必须有断言，且断言在失败时会红 |
| 一个提交塞多个任务 | 评审无法按任务核对 | 按任务提交，或至少在台账里分开 |
| 顺手重构 | 交付面失控，回滚困难 | 重构单独成需求 |

## 交接

冻结后把 `05-implementation.md`、提交范围、测试命令交给 QA（`org-role-qa`）与评审（`org-role-reviewer`），进入 06。

## 本次契约补充

RED/GREEN 证据必须各自包含唯一且非空的命令和输出，不能互借字段。工作未完成时保留 05 草稿并更新续做记录；重接手先核对工作区、输入版本与最近验证。外部操作结果不明时先查询，禁止直接重复发布、迁移或写入。详见 [生命周期](../../policies/lifecycle.md)。

续做记录保留原始请求、授权、后续消息处理及人工暂停。工程阶段、产物状态与运行等待原因分别说明。技术阻塞得到新线索后可在原授权内继续；人要求暂停时，进度询问、CI 或换会话不会自动解除。对外通知按项目授权发送并核对回执，未获发送授权则在当前会话交付结果。

## 模块与子模块

任务、实现与证据携带模块路径；本地编号与同路径前后阶段对应，跨模块引用使用 path#编号。显式模块依赖必须满足，根计划保留集成任务。组织、引用、命令与迁移见 [模块资料规则](../../policies/modular-artifacts.md)。
