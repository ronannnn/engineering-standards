# 设计：公共总览加注册的模块树

## 方案概述

根目录九份产物不变。可选 modules.json 注册相对模块路径、依赖与根公共基线修订；modules/<path>/ 中放 01–06 和 08，07 由根统一承担。树协调层调用既有阶段校验，再检查引用、冻结、修订和发布清单。

## 变更影响面

- [ ] 数据库 schema 变更
- [ ] 权限模型变更
- [ ] 跨模块接口变更
- [ ] 新增第三方依赖
- [ ] 性能基线变化

仅扩展标准自身的本地校验命令与组织方式，无业务模块接口或权限模型变更，保留既有阶段 check 接口。

## 架构与模块

gates/modular.py 解析清单和组织树校验；run.py 增加可选模块选择并在有清单时委托树检查，原模式不变。根与模块各有 Context，模块编号在路径内唯一；跨模块 AC/用例/任务使用 path#编号。根汇总模块的验收与测试注册表，不要求复制已有测试输出；根仍有自身集成测试。

## 接口契约

| 接口 | 请求 | 结果 |
|---|---|---|
| modules.json | version=1，modules 列表（path、depends_on、baseline） | 稳定路径和依赖图，JSON 严格解析 |
| --module path --stage NN | 根运行目录、模块路径或目录组 | 检查选中模块与依赖，公共输入一并验证 |
| --delivery / --all | 根运行目录 | 全发布/全归档，禁止局部模块绕过根发布 |
| init-module.py | 运行目录和模块路径，可选依赖 | 八份模块模板、清单及目录索引 |

## 数据模型与迁移

不适用：无业务数据库；原模式不迁移。采用模块模式先拆出模块资料并补模块清单、限定引用和公共基线；不自动移动冻结内容。

## 安全与权限

认证：沿用本地执行者；授权：沿用各阶段人工确认；敏感数据：不复制业务数据。JSON 不执行，路径限制在根 modules 内并拒绝外部符号链接和非法 slug，未知引用及循环返回定位。

## 兼容性

无清单原用法保持不变；出现模块产物却无登记时报错，避免漏检。模块 08 的依据为相对于模块目录的根 07 路径；签收规则不变。

## 性能与容量

同一模块每次检查加载所需阶段，按依赖排序；清单与输入大小以本地中小项目为目标，不引入网络和数据库。

## 可观测性

错误含 modules/<path>/文件名与行号；清单错误定位 modules.json；命令说明区分全局与模块局部自检，不把局部通过当作交付完成。

## 备选方案

### 方案 A：在根单文件中不断加入模块标题

- 做法：保持所有阶段单文件。
- 优点：脚本简单。
- 缺点：不满足多层文件夹和独立修改。
- 为何未选：用户明确要求按模块和子模块拆分。

### 方案 B：每个模块完全复制九阶段并独立发布

- 做法：各模块放完整九份文件，根只链接。
- 优点：可复用现有校验。
- 缺点：公共规则重复，交付和跨模块验收缺少统一入口。
- 为何未选：本次采用统一根发布与公共基线，减少重复签收。

## 决策记录

| 决策 | 结论 | 理由 | 代价 |
|---|---|---|---|
| 目录层次 | 组织作用，不隐含业务依赖 | 依赖需要显式可检查 | 清单需要登记依赖 |
| 公共资料 | 根 01–03 修订固定在模块 baseline | 公共内容变化不能静默放行旧模块 | 变更后需复核并更新模块基线 |
| 发布快照 | 根 07 列模块测试和评审修订 | 模块复验后旧发布签收不自动有效 | 清单随报告修订同步 |

## 验证方式

新增分层样例与反例测试，先记录 RED，再实现 GREEN；验证旧 51 项、模块/子模块、跨引用、循环、过期基线、交付快照、08 依赖与初始化失败不破坏已有文件。
