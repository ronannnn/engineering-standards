# 技术设计：按功能细分需求并方便审阅

## 方案概述

新增需求组织说明；模块能力保持不变，复杂需求写法从可选拆分改为先树后细节。同步需求模板、阶段技能、PM技能和入口说明；没有新增机器门禁判据。

## 变更影响面

- [ ] 数据库 schema 变更
- [ ] 权限模型变更
- [ ] 跨模块接口变更
- [ ] 新增第三方依赖
- [ ] 性能基线变化

## 架构与模块

新策略负责粒度和阅读顺序，现有模块策略负责登记、依赖与修订。需求技能和PM引导按功能拆分，模板增加导航与行为细节填写位置，README说明默认处理方式。

## 接口契约

不适用：本次为需求写作规则，无运行或业务变更。

## 数据模型与迁移

不适用：本次为需求写作规则，无运行或业务变更。

## 安全与权限

认证：当前本地会话；授权：只更新标准，不修改业务项目；敏感数据：目录示例来自用户提供的产品类型，不复制业务正文。

## 兼容性

不改frontmatter、二级标题或依赖格式；旧目录不自动失效，已有冻结产物迁移仍需修订与重新签收。

## 性能与容量

不适用：本次为需求写作规则，无运行或业务变更。

## 可观测性

Agent交付根总览和模块链接，说明待确认事项及修改范围，不能只发送长文。

## 备选方案

### 方案 A：按固定行数切分

- 做法：到行数即分文件。
- 优点：容易自动化。
- 缺点：割裂业务规则和验收。
- 为何未选：用户需要业务清晰而非物理切片。

### 方案 B：只增加折叠目录

- 做法：单文件加目录。
- 优点：改动小。
- 缺点：独立功能仍堆在同一文档。
- 为何未选：未解决审阅与修改粒度。
