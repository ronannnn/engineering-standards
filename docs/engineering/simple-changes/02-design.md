# 技术设计：默认直接实现当前需求

## 方案概述

重写兼容迁移策略为默认当前契约；常驻规则和项目配置声明例外来源；设计、编码、评审技能及模板同步。不新增机器内容判据，门禁仅改诊断措辞。

## 变更影响面

- [ ] 数据库 schema 变更
- [ ] 权限模型变更
- [ ] 跨模块接口变更
- [ ] 新增第三方依赖
- [ ] 性能基线变化

## 架构与模块

策略为公共规则，AGENTS作为常驻入口；项目配置记录已明确要求，模板承载当前契约、迁移与评审结论；角色和阶段技能引用同一策略，避免重新引入旧窗口和强制双写。

## 接口契约

不适用：本次只修改标准约定，无业务或数据变更。

## 数据模型与迁移

不适用：本次只修改标准约定，无业务或数据变更。

## 安全与权限

认证：沿用本地工具；授权：仅标准修改，不删除业务数据；敏感数据：不新增外部配置。输入校验、权限和真实错误处理不因简化而省略。

## 兼容性

本标准改默认行为而非具体业务API；已有显式兼容约束仍执行，不新增字段或删固定标题；存量冻结文档不直接改写。

## 性能与容量

不适用：本次只修改标准约定，无业务或数据变更。

## 可观测性

兼容例外须有具体来源和范围；临时实现说明退出条件；评审不把未保留旧路径视为缺陷。

## 备选方案

### 方案 A：只在README加一句话

- 做法：保留其余规则。
- 优点：改动小。
- 缺点：强制双写继续影响Agent。
- 为何未选：规则冲突未解决。

### 方案 B：删除全部迁移和错误检查

- 做法：以简化为由省略必要处理。
- 优点：代码少。
- 缺点：无法正确处理真实失败和数据。
- 为何未选：超出用户意图。

## 验证方式

逐项检查默认和例外文案；运行全部测试、样例及当前契约的临时设计夹具，确认不强制兼容窗口。
