# 兼容性与数据迁移

凡是改变数据结构、接口契约、配置格式的改动，都按本文件执行。目标只有一个：**上线能灰度、出问题能撤销、旧客户端不崩**。

## 兼容窗口

| 对象 | 最低要求 |
|---|---|
| 对外 API | 新增字段向后兼容；删除/改语义必须走版本（`/v2` 或显式版本头），旧版本至少保留两个发布周期 |
| 前端与后端 | 前端可先于后端发布，也可后于；接口变更必须向前向后都能跑 |
| 数据库 | 迁移脚本必须能在旧版本代码下执行完毕（代码先兼容新结构，再删旧结构） |
| 配置文件 | 新增配置项必须有默认值；删除配置项要保留一个周期的告警 |

## 迁移三原则

1. **可空加列、先写后读**：加列必须可空或带默认值；先部署写双写，再切读，再删旧列。禁止「一次性大改 + 停机」。
2. **正向与回滚成对**：每个迁移脚本都要有对应的回滚步骤，并在 02 的「数据模型与迁移」写清。回滚步骤本身也要在预发演练过。
3. **旧数据显式处理**：存量数据是回填、兼容还是忽略，必须写清楚；「应该没问题」不算处理。

## 回填与双写

- 回填要有幂等性：重复执行结果一致。
- 回填要有进度与中断恢复方式，避免大表单事务。
- 双写期要写明时长与退出条件；退出前必须验证读路径已全部切到新结构。

## 契约测试

改了接口的，必须在 06 的测试报告里体现契约测试：请求/响应字段、错误码、空值与边界。只测 happy path 不算契约测试。

## 回滚验证清单

在 07 的「回滚方案」里逐项确认：

- [ ] 应用可回滚到上一个版本（镜像/包可获取）
- [ ] 数据迁移可逆向，或明确标注不可逆并给出数据保留方案
- [ ] 配置与开关可回滚
- [ ] 回滚后健康检查与关键指标有判定标准
- [ ] 回滚操作有负责人与预估耗时

未勾完的项，必须在 07 里写清为什么可以接受，并由人签收。

## 禁止事项

- 禁止在业务低峰期「赌一把」执行不可逆迁移。
- 禁止用「先上线再看」代替兼容设计。
- 禁止删除旧字段/旧接口而不保留一个周期的弃用告警。
