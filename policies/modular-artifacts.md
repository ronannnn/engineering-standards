# 按模块和子模块组织工程资料

## 目录怎么放

小需求继续使用原来的九份文件。涉及多项独立业务能力时，从01需求分析就按功能和必要的子功能拆分，不能等长篇产品规格写完才考虑目录。根保留公共总览，细节进入登记模块；粒度和用户阅读顺序见 [需求拆分与阅读](requirements-organization.md)。目录示意：

```text
docs/engineering/shop-update/
├── 01-requirements.md          # 整体目标与跨模块需求
├── 02-design.md                # 公共架构、接口边界
├── 03-ui-design.md             # 公共设计系统
├── 04-tasks.md                 # 整体任务、模块依赖与集成计划
├── 05-implementation.md        # 集成实现证据
├── 06-test-report.md           # 验收汇总和跨模块测试
├── 06-review-report.md         # 整体评审
├── 07-delivery.md              # 本次发布统一交付
├── 08-retro.md                 # 整体维护与复盘
├── modules.json               # 本次变更的模块清单
└── modules/
    ├── README.md              # 工具生成的模块索引
    ├── users/
    │   └── access/            # 用户管理/权限子模块
    │       ├── 01-requirements.md
    │       ├── 02-design.md
    │       ├── 03-ui-design.md
    │       ├── 04-tasks.md
    │       ├── 05-implementation.md
    │       ├── 06-test-report.md
    │       ├── 06-review-report.md
    │       └── 08-retro.md
    └── orders/
        └── refund/            # 订单/退款子模块，同样的八份文件
```

目录分组不需要每层都放文件。需要独立管理的模块或子功能才登记为一个节点，也可以同时登记父模块与子模块。层级只表达组织关系；实际业务依赖必须显式填写，不默认子目录依赖父目录。

模块共享根 01–03 的整体约束，但自己的同阶段产物仍写模块特有内容；无界面可按原规则说明 03 不适用。公共架构、设计系统只在根维护一份，模块引用它们并写差异。模块 07 不重复创建；发布回滚和跨模块故障处置由根统一记录。

清单只列本次需求或发布涉及的模块；它不是整个项目永久不变的模块台账。后续迭代另建运行目录并关联本次记录，不能通过取消登记来隐去仍属于本次范围的模块。

## 创建模块

先用原脚手架创建根目录，再运行：

```bash
./scripts/init-docs.sh shop-update
python3 scripts/init-module.py docs/engineering/shop-update users/access
python3 scripts/init-module.py docs/engineering/shop-update orders/refund --depends-on users/access
```

工具生成模板、登记清单并更新 `modules/README.md`，重复执行会拒绝覆盖。先读根公共产物；脚手架记录当前修订用于后续复核，不代表这些草稿已经签收。根目录仍须逐阶段完成公共产物。

清单格式如下。人工维护时使用相同字段；工具生成的索引不是另一份事实来源，清单为准。

```json
{
  "version": 1,
  "modules": [
    {
      "path": "users/access",
      "depends_on": [],
      "baseline": {"01": 1, "02": 1, "03": 1}
    },
    {
      "path": "orders/refund",
      "depends_on": ["users/access"],
      "baseline": {"01": 1, "02": 1, "03": 1}
    }
  ]
}
```

路径使用多层 kebab-case，相对根 `modules/`；拒绝绝对路径、`..`、越界符号链接、未知字段、重复路径、未知依赖和循环依赖。清单必须非空。出现模块产物却未登记会报错，避免只检查总览而漏掉细节。

## 编号和引用怎样对应

局部编号继续用 `REQ-0001`、`FR-1`、`AC-1`、`任务 1`、`T-1`。它们在所属模块内唯一；跨模块的完整身份由“模块路径 + 编号”组成。根目录编号代表整体，模块编号不因其他模块新增而重排。

- 权限模块验收：`users/access#AC-1`。
- 退款模块验收：`orders/refund#AC-1`。
- 模块用例：`orders/refund#T-1`。
- 模块任务：`orders/refund#任务 1`。
- 模块产物与需求身份：`orders/refund#REQ-0001`、`orders/refund#FR-1`，实际文件位置为 `modules/orders/refund/01-requirements.md`。

01 到 06 依照同一模块路径对应，沿用各文件的固定依据链。模块自己的矩阵检查自己的 AC；跨模块协调在根计划和测试报告中汇总。不要把另一个模块的裸 `AC-1` 当成本模块的同名需求。

根 04 的验证矩阵必须覆盖整体 AC 加本次全部模块 AC；“覆盖任务”可引用根任务或模块全限定任务，不存在的任务不能作为依据。根 06 的矩阵也覆盖这份完整集合。可直接引用模块实际用例，省去复制命令和输出：

| 验收标准 | 是否有已执行用例 | 依据用例 |
|---|---|---|
| orders/refund#AC-1 | 是 | orders/refund#T-1 |

限定用例必须存在、结果通过并对应同一个限定 AC。根测试报告仍需有自身的跨模块集成或系统验证；不能把“各模块单测通过”当成“组合后一定正常”。格式校验能保证引用一致，真实集成质量由实际测试和评审确认。

## 冻结、公共基线和模块依赖

每个模块都走原签收规则：01 必须人确认；02/03 按风险确认；04/05/06 可机器冻结；整份不适用仍需人确认。根 `--stage NN` 会检查根与各模块到该阶段的内容和上游冻结情况。

局部执行时根公共输入必须有效冻结；`baseline` 固定根 01/02/03 的修订。只检查当前阶段用到的公共基线，未来草稿不提前阻塞早期阶段。公共文件重新冻结并增加修订后，模块基线失配会报错；先复核影响、撤销受影响下游冻结并重跑，再更新基线，不自动修改数字掩盖过期设计。

声明 A 依赖 B 时，推进 A 的阶段需要 B 同阶段已冻结；阶段 07/08 以 B 的 06 为模块前置。这样可以分模块推进，又不能跳过已经声明的上游。目录父子关系本身不添加这种依赖。

```bash
# 全部模块及整体计划自检
python3 gates/run.py docs/engineering/shop-update --stage 04
# 单个模块，或 users 下面的整个目录组；自动包括必要依赖
python3 gates/run.py docs/engineering/shop-update --module orders/refund --stage 06
python3 gates/run.py docs/engineering/shop-update --module users --next
# 本次发布与完整归档必须检查整体，不能用 --module 缩小范围
python3 gates/run.py docs/engineering/shop-update --delivery
python3 gates/run.py docs/engineering/shop-update --all
```

`--module` 只与 `--stage` 或 `--next` 配合；不能单独执行模块 07。局部通过仅表示该模块及前置条件通过，不能宣称整个发布已完成。

## 统一交付和维护

根 07 的“遗留与后续”下增加以下清单，模块测试和评审必须有效冻结、结论可发布/可合并，修订与实际文件一致：

| 模块 | 测试修订 | 评审修订 |
|---|---|---|
| users/access | 1 | 1 |
| orders/refund | 1 | 1 |

每个本次登记的模块恰好一行，不能遗漏、重复或增加未知模块。模块重新测试或评审导致修订变化时，旧发布清单不再匹配，必须重新核对并签收。

根 07 冻结后才能完成模块 08。模块 08 的 `依据` 为相对于模块目录的根 07 路径，由脚手架自动计算；整个模块层级改变时需要同步调整。模块复盘分别记录负责人、故障、改进任务；根复盘汇总跨模块问题。

`--delivery` 要求根 01–07 及各模块 01–06 有效冻结，不要求任何 08。`--all` 另外要求根和各模块 08 有效冻结。CI 中任意深层模块文件变更都会触发其根运行目录的整体合并检查。

## 从旧目录迁移

旧九份文件继续可用，不自动拆文件。确需采用模块方式时：先确定本次范围，按原规则撤销受影响冻结并增加修订；创建模块、移入对应资料并保留引用；补根集成计划与验收汇总、公共基线及发布修订清单；逐阶段校验后重新签收。未变化的上游无需重复签收。

功能需求的 `FR-N` 编号在同一份需求文件内不得重复；不同模块可以复用局部编号，跨模块引用必须携带模块路径。
