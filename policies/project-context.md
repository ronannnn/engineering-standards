# 项目接入说明

首次接入按 [SETUP](../SETUP.md) 检查和配置；自然语言、技能和脚本的分工见 [使用约定](usage.md)。

本仓库规定协作、证据和检查方法。开发语言、框架、设计语言、组件库和部署工具由具体项目决定，`adapters/` 仅是可选示例。

每个项目在 `docs/engineering/_custom/project.md` 记录下面的信息；已有文档可直接链接，避免重复维护。每次接手任务先读这里及相关目录的 `AGENTS.md`。缺失信息先从代码和配置核实，不能编造。

| 项目事项 | 填写内容 |
|---|---|
| 产品与用户 | 给谁用、主要任务、成功表现、明确不做的事 |
| 技术与目录 | 语言及版本、框架、模块入口、已有架构说明 |
| 启动与环境 | 安装、启动、环境变量名称和测试数据准备；不写密钥值 |
| 验证命令 | 单元测试、集成测试、构建、静态检查、安全扫描的具体命令及预期结果 |
| 设计系统 | 有界面时填组件库、字体、颜色和布局规范、已有页面；没有界面写理由 |
| 发布与恢复 | 发布目标、环境、验证方法、回滚方法、重复执行如何识别 |
| 维护责任 | 服务负责人、告警入口、故障升级路径、后续任务位置 |
| 执行授权 | 可发起任务的人或规则、允许修改的范围、外部操作与签收边界；记录来源，不写凭据 |
| 任务接入与工作区 | 原始请求和后续消息如何关联任务、谁负责派发、工作区隔离或共享写入方法 |
| 对外通知 | 允许回复的渠道、发送身份、何时通知、如何查询回执；未配置渠道时在当前会话报告 |
| 标准接入记录 | GitHub 仓库地址、分支或版本、实际来源提交、项目内标准位置及项目自改情况、方式和日期；技能入口与 CI 是否实际验证 |
| 明确的兼容要求 | 没有则写“无，按当前契约直接变更”；有则记录来源、对象和范围，临时保留项补退出条件；不自行推断 |

后台、表单和工作台优先让用户顺利完成任务；展示页面按项目目标决定表现力。设计检查覆盖真实内容、加载/空/错/无权限等状态、键盘操作、不同屏幕及实际渲染结果。通用层不强制颜色、字体或视觉风格。

角色覆盖继续使用 `_custom/roles/<role>.toml` 与个人 `.user.toml`。它们是按技能约定读取的配置，不是自动加载的权限系统。执行者需读取基础规则、团队文件、个人文件并按顺序合并；若工具未提供合并器，应明确记录人工解析结果，不能声称脚本已执行。个人文件自行加入 `.gitignore`。

需要按模块与子模块拆资料时，公共约束仍在项目和根文档维护，按 [模块资料规则](modular-artifacts.md) 注册模块、依赖及公共基线。

使用运行平台时，另记任务、授权与暂停记录的持久化位置、执行工具的权限校验点、消息去重和重启恢复方法；未具备的能力明确写“未接入”。这些是可选接入事项，不要求选用特定模型、语言、GitHub 或飞书。
