# 交付

交付不是「发出去」，而是「可回滚、可观测、有人确认」。本文件规定 07 阶段的判定标准与 PR 规范。

## 进入 07 的前置条件

- `06-test-report.md` 结论为「可发布」且已冻结。
- `06-review-report.md` 结论为「可合并」且已冻结。
- 两者的门禁均已通过：`python3 gates/run.py <run-dir> --stage 06`。

任何一条不满足，回到 05 修复，不得进入交付。

## 07 必须回答的五件事

1. **改了什么**：逐条列出功能、修复、配置、数据、依赖变更。
2. **凭什么可发**：CI 五项（单元、构建、静态检查、安全扫描、标准门禁）全部通过并有证据。
3. **怎么发**：步骤、负责人、时间窗口、前置依赖。
4. **怎么退**：触发条件、步骤、数据是否可逆、预估耗时。
5. **怎么知道正常**：健康检查、关键指标与阈值、观察窗口、日志检索方式。

## AI 参与度声明

按五个环节各填一个等级，并写一句「人做了什么、AI 做了什么」：

| 等级 | 判定 |
|---|---|
| 人工独立 | 人完成，AI 只给被动建议 |
| 人工主导 | 人给主体内容或每个关键决策，AI 补细节 |
| 人工引导 | 人给方向与约束，并多次修正 AI 产出 |
| 人工把关 | AI 完成，人审阅、选择或否决，不提供实质内容 |
| 模型自主 | AI 自主完成，人只设目标或接受结果 |
| 不适用 | 该环节不存在（例如无界面时的验收测试） |

等级用于度量流程把人从实现里挪出去的程度，不用来评分。美化数据会让 08 的复盘失去依据。

## PR 规范

- 一个 PR 对应一个运行目录（`docs/engineering/<slug>/`）；不要把两个需求塞进一个 PR。
- PR 描述必须包含：变更摘要、关联运行目录、验证证据（命令与结果）、AI 参与度、回滚方案链接。
- 门禁在 PR 上跑；门禁红了不允许合并。
- 合并前确认 07 的签收字段已填写。

## 部署与观察

- 部署后 30 分钟内按 07 的观察项检查一次；次日再看一次。
- 出现 07 中列出的回滚触发条件，直接执行回滚，不在线上边修边猜。
- 回滚后把过程写进 08 的「过程偏差」，并在标准改进项里登记。

## 线上问题回流

线上缺陷必须走同一套流程：新建运行目录（可复用 01 的轻量路径），在 01 写清现象与影响面，在 06 写清回归用例，在 08 复盘为什么此前没拦住。
